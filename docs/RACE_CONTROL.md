# Race Control development preview

This source build adds a Race Control workspace. The already-running PS5 receiver was left untouched during development; the backend additions load on the next normal application restart. It is **not yet the completed broadcast release** and the existing downloadable beta packages do not include it.

## Current workflow

1. Open **Race Control**. Create a league, select it, and create an event.
2. Enter the exact allowed browser origins (for example `http://192.168.1.20:8090,http://127.0.0.1:8090`). Enable the group listener deliberately. Port 8090 exposes the group surface, not the local settings or maintenance API.
3. Choose host-only to suspend local telemetry and microphone acquisition without changing saved settings. Leave this unchecked when the host is also driving.
4. Issue driver or spectator invitations and copy them when shown. Admitted members have separate credentials; revoking an invitation does not revoke existing members. Remove a participant to revoke their access.
5. Drivers use **Group Connection** in their installed app, enter the host address and invitation, and select accepted sharing categories. Hosts approve pending members. Spectators open the host's `/group` page and use a spectator invitation.
6. Start an application session. Session buttons do not start or control a GT7 race. The table is labelled connected-group timing; supplied telemetry is not identity verification.
7. Issue global flags or public messages. Instructions are individually cancellable. Driver message acknowledgements are separate from delivery receipts.
8. Create a Broadcast Studio workspace. Add graphics, choose primary/comparison entries, and arrange their coordinates and sizes on the 1920 x 1080 canvas. Save draft does not affect program; **Take to program** publishes the draft.
9. Issue an OBS output URL. Keep the entire URL, including its fragment, private. Add it as a Browser Source at 1920 x 1080 and 30 FPS. The output is transparent, read-only and contains no local application controls. Keep the fragment intact so refresh/reopen can authenticate again.
10. End the session and explicitly confirm final results. Current classification is provisional and spatial/race-result validation is still in progress.

## Implemented renderer templates

Timing tower, session bar, flag banner, race-control message, driver lower third, selected-car telemetry, head-to-head comparison, track map, grid/results panel, league/event slate, fastest lap announcement, class leader panel, penalty/investigation notice, podium, and sponsor rotation — 15 total. Unavailable telemetry is labelled; no speed, fuel or gap is invented. The composite uses one subscription.

The five newest templates reuse existing data only: fastest lap and podium read the same `best_ms`/`position` fields the timing tower already shows; class leaders groups connected entries by `identity.class_name` (no invented classing); the penalty/investigation notice shows the latest **public** steward decision (private decisions never reach it — verified via `filter_snapshot`, not just assumed); sponsor rotation cycles a league's enabled, uploaded sponsor logos on a deterministic ~4s interval keyed to session timeline (no client-side timers to get out of sync between viewers). All five were verified rendering live against a real demo session and a real uploaded sponsor asset, not just built and assumed correct. One real thing this caught: sponsor logos live in the league's branding, which a running group intentionally freezes into `branding_snapshot` at session start (so on-air branding can't change mid-session just because a host edits it) — a sponsor added after a session has started won't appear on air until the next session start, which is correct, existing behavior, not a bug in the new template.

## Ten sampleable broadcast styles

Beyond the Formula/Endurance pair, eight more genuinely distinct visual presets are implemented and selectable per workspace: **Minimal** (flat, hairline borders, monochrome), **Neon Esports** (glow accents on a dark gradient), **Vintage Poster** (cream background, serif type, double rule), **Rally Stage** (hazard-stripe top bar, monospace timing), **Oval Speedway** (bold block header band, heavy display type), **Carbon GT** (carbon-fibre texture, cool blue accent), **Heritage GP** (sepia tones, plaque border, classic serif), and **Holo HUD** (frosted glass panels via `backdrop-filter`, cyan glow, monospace). All ten are built from system-safe font stacks only (Arial/Georgia/Consolas/Segoe UI and similar) — no external font or network loading, consistent with the app's local-first requirement.

Broadcast Studio's **Style gallery** (inside "Workspace and shared selections") renders all 10 as live swatches — each one is the real Timing tower graphic rendered in that style with the workspace's actual current data, not a static mockup — so a host can compare them side by side and click to apply one to the draft before Take.

## Data and network boundaries

Group publication defaults to basic timing, identities and positions. Detailed telemetry, fuel and strategy require opt-in. Host administration remains protected by the application's existing local pairing credential. The public listener uses hashed invitation/member/output credentials, explicit browser origins, short-lived subscription tickets, separate authenticated native publishing, bounded native frames and rate limits.

Use LAN access only on a trusted network. Remote use requires a user-managed secure network or HTTPS/WSS reverse proxy with WebSocket upgrades. There is no relay or account service. The app does not configure router forwarding or TLS automatically.

Relevant design references: [OWASP WebSocket security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html), [OWASP file uploads](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), and [OBS Browser Source](https://obsproject.com/kb/browser-source).

## Load-test results (this laptop, not the original Orange Pi target)

See `docs/group-load-test-validation.json`, produced by `scripts/group_load_test.py`. That script runs the real app, enables the LAN group listener, drives the built-in synthetic league demo at 4/8/16 drivers, and opens 1/8/32/60 concurrent WebSocket overlay subscribers (the same connection type an OBS Browser Source or spectator page uses) against it, measuring the actual process tree's CPU/RSS and per-connection snapshot delivery latency.

Key finding: RSS stays modest (80-103 MB across the whole matrix, 4-16 drivers included) and driver count barely moves it, but **viewer/overlay count is the real cost driver, not driver count.** Each subscriber connection filters and deep-copies its own snapshot on the single asyncio event loop roughly every 200 ms; CPU scales up sharply with viewer count regardless of driver count (~12-13% of one core at 1 viewer, ~41-59% at 8, 1.2-1.4 cores at 32, 1.1-1.5 cores at 60 — i.e. well past one core), and snapshot delivery latency degrades in step: a healthy p50 of ~220 ms at 1-8 viewers holds up to roughly 250-360 ms at 32 but climbs to 480-690 ms (p95 up to ~900 ms) at 60. The 64-connection hard cap prevents unbounded growth, but does not prevent latency degrading well before that cap is reached — 32 concurrent overlays is already using well over a full CPU core for snapshot delivery alone.

**Attempted fix and what was actually learned.** `GroupService.raw_snapshot()` (the per-entry classification and field-availability computation) now caches its result for a 150ms window keyed to the group/session, invalidated immediately on any group mutation ([backend/app/group/service.py](../backend/app/group/service.py)), so concurrent viewers within one ~200ms tick share a single computation instead of each redoing it. This is correct and kept, but repeated re-tests of the worst case (16 drivers, 60 viewers) across several runs — both before and after the change — swung between roughly 690ms-1.2s p50 and 94-151% CPU on this laptop, a spread wide enough that the fix's actual impact is within the noise of a shared, single-machine measurement rather than a clearly proven win. What the fix does *not* explain is why the same order-of-magnitude degradation persisted regardless. Re-reading `/group-api/subscribe` in [backend/app/group/public.py](../backend/app/group/public.py) turned up a more likely culprit: every single loop iteration (every ~200ms, per connection) calls `service.authenticate(ticket['token'])`, which runs `GroupRepository.auth()` — a fresh `sqlite3.connect()` plus a query — via `asyncio.to_thread`. Python's default thread-pool executor caps concurrent worker threads at `min(32, cpu_count+4)`; with dozens of connections each issuing a blocking DB open every tick, that pool is a strong candidate for the real bottleneck, independent of whatever `raw_snapshot()` costs. The ticket already carries a resolved `principal` (`ticket['principal']`) that the loop currently ignores in favor of re-authenticating from the raw token every time.

This is flagged rather than fixed in this pass: reducing re-authentication frequency changes how quickly an already-open overlay/spectator connection notices a host-side revocation (a genuine security property, exercised by `test_group_admission_revocation_and_public_boundary`), so it deserves its own deliberate design (e.g. re-validate every 2-3 seconds instead of every message, or a short-TTL auth cache with immediate invalidation on `revoke()`) and dedicated test coverage, not a quick patch appended here. This is the concrete next step for anyone picking up broadcast scaling work. Full numbers for all 12 driver×viewer combinations are in `docs/group-load-test-validation.json`.

The overlay page itself was verified by enabling the LAN listener and opening a real scoped `/overlay/<workspace>#access=...` URL directly (not just through the SPA router): the composite renders the timing tower and session bar correctly with real demo data, and `getComputedStyle` on `<html>`, `<body>` and `#root` confirms all three are genuinely `rgba(0,0,0,0)` (fully transparent), not just visually dark — the requirement OBS Browser Source depends on. No console errors. This was done in Chromium (the built-in browser pane), which is the same browser family OBS's Browser Source embeds (CEF), but not literally inside OBS Studio itself — that remains unverified, along with a multi-hour soak and real concurrent driver *publishers* at scale (the load test above scales synthetic driver telemetry through the existing single-process demo tick, not independent publisher connections).

## Broadcast Action Director and spatial strategy/coaching (Phases 0-8)

This build adds an action-director layer on top of the existing timing/graphics system - automatic battle detection, stewarding-cue overlays, a net-position/pit-window projector, tyre-heat and micro-coaching alerts, and fuel/clean-air strategy advice - plus the v3 world-frame track model wiring that all of it depends on. It was built and tested phase by phase; each phase's tests were green before moving to the next, and the full backend suite (414 tests) passes with the whole thing wired in. Frontend changes typecheck clean (`npx tsc -b`) after each step.

**Phase 0 - v3 track wiring.** `TrackService` (`backend/app/track_service.py`) and its `TrackProgress`/`Progress` world-frame model (`backend/app/track_model.py`) are now live in `Runtime.consume_track_service()` and in `GroupService.classification()`, alongside the pre-existing legacy 2D `TrackMap`. The two systems run in parallel by design: `TrackMap` still owns recognition/learning, while `TrackService` supplies race-distance progress once a v3 model exists for the bound layout.

**Phase 1 - distance model.** `group/history.DistanceHistory` is a bounded, decimated (≤5 Hz), monotonic-in-distance time series of `(common_timeline, race_distance_m)` per entry, built in `GroupService.classification()` once a v3 model is bound and the sample is fresh; a backward jump under 5m is treated as clamp-worthy noise, a larger one as a reset. `interval()` looks up a following car's actual time-at-distance for a real gap (not a linear estimate); `gap_uncertainty()` combines both cars' clock uncertainty in quadrature. `group/pit.PitTracker` detects pit-in/pit-out from position, speed and lap-count state and produces a completed-stop record GroupService accumulates in `pending_pit_stops`/`g['pit_stops']`. Tests: `tests/test_history.py` (or equivalent distance-history tests) and pit-tracker coverage in `tests/test_projection.py`.

**Phase 2 - Battle Index.** `group/battles.BattleEngine` runs at 2 Hz (`GroupService.battle_loop`) over raw (undelayed) classification, heat-scoring every adjacent on-track pair from gap, closing rate and recent-swap continuity, with hysteresis states (forming → hot → critical → ended) and a 90s per-battle-per-alert-kind cooldown. The desk sees battles via `GET /api/group/battles`, can dismiss one (suppresses further alerts, keeps it listed) or focus it into a workspace. Drivers never receive battle data in their own app - `filter_snapshot()` always zeroes `battles` for a driver principal. Tests: `tests/test_battles.py` (14 tests, including a full async `GroupService` integration test that drives two synthetic cars around a circle and confirms both a real 2 Hz-computed battle and its driver-side redaction).

**Phase 3 - focus-to-overlay.** `GroupService.focus_battle()` turns a desk battle pick into a workspace draft (or immediate take), with a 30s grace period (`engine.find()`) so a momentary battle-state flicker doesn't drop the on-air take. `POST /group-api/workspaces/{id}/focus-battle` and the `battle_tag` graphic template (500×120, basic sharing only) expose it to Broadcast Studio.

**Phase 4 - automated stewarding graphics.** Recording a public `Decision` while stewarding isn't paused now calls `group/steward.enqueue_steward_cue()`, which schedules a timed, priority-preempting overlay cue (`PRIORITY` dict, `MAX_CUES=16`, default 10s). `active_cue(cues, now)` is a pure function of the cue list and current time, so a delayed broadcast or a replay viewer reproduces the exact same cue history rather than whatever the host's live clock happened to show. The host can cancel a pending cue or pause/resume auto-stewarding entirely (`PUT /api/group/steward-cues/paused`). A real gap was found and fixed here: there was previously no UI path to record a *public* decision at all (only private) - "Record public decision" was added alongside the existing button in `RaceDesk.tsx`.

**Phase 5 - net position and pit-window projector.** `group/projection.py` is pure math: `stops_needed()`/`stop_cost_s()`/`pit_window()`/`project()` take each entry's fuel state, gap to leader and a resolved pit-loss/refuel-rate, and return a ranked net-position table with per-entry uncertainty and "close call" flags (net-gap deltas smaller than the pooled uncertainty). `GroupService._compute_projection()` resolves those inputs every 0.5 Hz (`projection_loop`); pit loss and refuel rate prefer a host-entered value, then a value learned from real stop history (`learned_pit_loss`/`learned_refuel_rate` in `group/pit.py`, needing genuine stop data, never a guess), then "unavailable". `_public_projection()` is the redacted broadcast/driver view: rank, stops, net gap, window, pit-loss source and value - never a raw fuel litre for any car but yourself. The `net_order` graphic (800×640) surfaces it, gated on sharing *both* `fuel` and `strategy` (the graphics registry's advertised requirement was a real bug found in this pass - see "Issues found and fixed" below).

**Phase 6 - tyre heating-rate alert.** `tyre_heat.TyreHeatMonitor` EMA-smooths (α=0.2) each tyre's surface temperature against a per-track-position baseline (β=0.3 per bin visit), then fits an OLS slope over the trailing 20s of anomaly (actual minus baseline) to catch a *genuinely climbing* tyre rather than a momentarily hot one. `engineer.Rules._tyre_heat_events()` applies entry/exit hysteresis and a 120s per-tyre / 60s global cooldown, gated by a 2-lap warm-up and any active pit-out suppression window - written as a hand-rolled method rather than fitting the generic per-key rule pattern, because it needs to reason across all four tyres and carry cross-tick state. `WheelDash.tsx` shows a "▲" indicator per heating tyre.

**Phase 7 - spatial braking and micro-coaching (live path only).** `spatial_coaching.SpatialLap` is a 10m-binned trace (elapsed time, min speed, max brake, max throttle; unvisited bins are `NaN`, never a guessed value) built per lap in `Runtime.consume()`. `LiveBrakingTracker` detects a braking episode per corner and deliberately keeps it open past brake release to also capture throttle-reapplication distance and exit speed 50m further on. `corner_report()` compares the latest completed lap to a reference lap per corner: a time gain needs no cause attribution ("keep that"), a loss is attributed to entry (braking onset), min-speed or exit-throttle timing via whichever side of the corner (entry vs exit) actually lost more time, each gated by a real threshold so a difference under the noise floor isn't reported as a cause. Reachable by voice as "how was turn N" / "what cost me the most" / "compare my braking" via `voice.ALIASES`/regex, not the fixed 100-entry `requests.CATALOG` (adding entries there would have broken its intentional `assert len(CATALOG)==100`). **Deferred**: a recorded/post-session corner-report UI - only the live in-race coaching path was built.

**Phase 8 - strategy upgrades.** `analytics.fuel_scenarios()` proposes a SAVE branch (feasible only under `config.max_save_percent`) and a SPLASH branch (needs a known pit loss; adds refuel time only when the rate is known, otherwise the text says so rather than silently omitting it) on a fuel deficit or an explicit "what are my fuel options" ask, overriding to SAVE when a cheaper SPLASH would cost a track position on a known gap; `cost_per_l` is OLS-learned from ≥6 comparable laps with ≥3% fuel-used spread, else a labelled default. `clean_air.pit_advice()` runs only on a driver's own app, only when connected to a group that opted in to `share_traffic_with_drivers`: it projects each shared traffic car's own rejoin position for staying out 0-5 extra laps (using that car's own lap pace, never yours), flags ones that would land within a 2s window ahead, and recommends the cheapest lap count only if it beats boxing now by ≥1s - the answer text always describes what boxing *now* would rejoin into, with the recommended lap count as the fix, matching how a real spotter would phrase it. `Runtime.clean_air_advice()` wires this from the group connection's own last-published state and appends its text to the "when should I pit" voice answer, returning nothing rather than a guess if any input (connection, sharing opt-in, bound track length, fuel/pace data) is missing. **Known non-wiring**: `config.Settings.tyre_heat_rate_c_s`/`tyre_heat_anomaly_c`/`coaching_min_loss_s` exist as schema fields but aren't yet read as dynamic overrides - Phase 6/7's thresholds are still the hardcoded constants named above.

### Issues found and fixed during this build (not just the tests written alongside them)

- `GroupService.create_group()` omitted `pit_stops`/`steward_cues`/`cued` from the new-group dict, a real `KeyError` once stewarding was exercised.
- Tyre-heat hysteresis only accumulated while a rule *wasn't* suppressed (warm-up laps, post-pit window), so an already-sustained heating condition needed a full fresh 8s persist window after suppression lifted instead of firing immediately - fixed by always running the hysteresis tracking and gating only the final emission on suppression.
- `LiveBrakingTracker` originally closed a braking episode at brake release, before the spec's required exit-speed measurement 50m later - required tracking release separately from finalization.
- `corner_report()`'s time-gain ("keep that") case was nested inside episode-matching and silently skipped when no braking episode was available for that corner.
- `clean_air.pit_advice()`'s answer text was built from the *recommended* option's blocking traffic instead of the "box now" option's, contradicting its own template wording.
- `GroupService.filter_snapshot()`'s new `traffic` field for drivers computed each car's `battle_state` from the driver-view `battles` list *after* that list had already been zeroed out for drivers (drivers never see raw battles) - it always came back `None`. Fixed by deriving battle state from the raw battle list before that redaction runs.
- `group/public.registry()` advertised the `net_order` graphic as needing only `fuel` sharing, while `_public_projection()` actually gates its data on `{'fuel','strategy'}` both being shared - a host who enabled fuel sharing but not strategy would add the graphic and see it permanently "unavailable" with no indication why. Fixed to advertise both categories; `docs/BROADCAST_GRAPHICS.md`'s table and graphic count (26 → 28) were also out of date and have been corrected.

A follow-up adversarial code-review pass (after the phases above were already green) found three further real bugs, all now fixed with regression tests:

- `clean_air.pit_advice()`: the "laps stuck behind traffic" multiplier, `min(MAX_STUCK_LAPS, laps_left - k)`, was never floored at 0. Once a candidate `k` (extra laps to stay out) exceeded `laps_left`, the multiplier went negative - and since the recommender picks the *lowest*-cost option, it would recommend the largest available `k` (e.g. "stay out 5 laps" with 2 laps left in the race). The same collapse happened whenever `laps_left` was unknown (a timed/unclear-length race), silently zeroing the entire stuck-traffic penalty. Fixed by capping the candidate `k` range at `laps_left` itself (when known) and clamping the multiplier at 0 as a second layer of defense.
- `GroupService.entry_update()`: reassigning an entry to a different driver updated only the *new* driver's `entry_id`; the driver reassigned *away* from that entry kept a stale `entry_id` still pointing at it, and their join credential is not revoked by a reassignment (only by removal). `filter_snapshot()`'s "is this my own row" check matched on that stale id, so the old driver's still-valid session would see the row through the *new* driver's own (possibly broader) personal sharing consent instead of the group's publication redaction - a real privacy leak across a driver swap. Fixed by clearing the outgoing driver's `entry_id` on reassignment, plus a defense-in-depth check in `filter_snapshot()` that verifies the entry's current `participant_id` still points back at the principal before treating a row as their own (mirroring the existing "Publishing lease reassigned" check already enforced on the telemetry-write side).
- `group/projection.project()`: `any_stop_needed` was only ever set from entries whose stop-count was actually known; entries with unavailable fuel data (the normal state for every driver in the opening laps, before enough comparable laps exist) never contributed to it. So whenever *every* entry's fuel data was still unavailable, the function returned the "No stops required by current estimates" all-clear summary with an *empty* entries list - actively misreporting "unknown" as "confirmed no stop needed" and dropping the per-entry "fuel data unavailable" status rows that would have explained why. Fixed to track unknown entries separately and only report the all-clear when every entry's stop-count is actually known to be zero.
