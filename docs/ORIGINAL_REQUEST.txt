4. PROTOCOL IMPLEMENTATION AND VERIFICATION

Protocol reference checked September 23, 2026; recheck upstream during implementation and pin a commit. Read src/GT7UDPParser.cpp and src/GT7UDPParser.h as well as the README. The current base includes A, B, ~, and C variants. Its README examples and structure descriptions can differ from the header: the header defines PacketC as extending PacketTilda, and uses readData(). Verify inheritance, byte offsets, and method names instead of copying a README example blindly.

Protocol starting points to confirm against the pinned source:

- Send heartbeat traffic to the console's UDP port 33739; receive telemetry locally on UDP port 33740.
- Heartbeat payload selects the requested variant: A, B, ~, or C.
- Expected packet lengths: A=296, B=316, ~=344, C=368 bytes.
- Salsa20 key: the first 32 ASCII bytes of "Simulator Interface Packet GT7 ver 0.0".
- Extract the little-endian seed at bytes 0x40 through 0x43.
- Variant XOR constants: A=0xDEADBEAF, B=0xDEADBEEF, ~=0x55FABB4F, C=0xDEADBEEF.
- The eight-byte nonce is the little-endian concatenation of (seed XOR variant constant), then seed. Validate with independent fixtures rather than trusting an encrypt/decrypt round trip written from the same assumptions.

Use a configurable heartbeat interval, initially around five seconds. Support explicit variant selection and controlled automatic fallback when an extended variant is unavailable. Avoid continuous probing and variant switching during a working session. A quiet console in a menu is not proof that a variant is unsupported.

Parse explicit little-endian offsets; do not depend on native struct alignment. Verify packet length and decrypted magic before reading fields. Reject malformed/truncated datagrams safely. Reset unavailable extension fields to null when a shorter variant arrives; never retain stale C fields from an earlier packet.

Support nominal full-rate reception around 60 Hz without assuming every packet arrives at that rate. Record observed rates, duplicates, reordering, sequence gaps, resets, unexpected senders, and parse/decryption failures. Apply a documented sequence-number and wraparound policy. A parser exception must never kill reception.

Use monotonic timestamps for intervals, scheduling, and latency, plus UTC timestamps for storage and presentation. Retain source packet IDs and version information. Differentiate network gaps from application queue drops. Validate finite numbers, sentinels, signedness, and plausible ranges without silently inventing replacements.

Implement reconnect/backoff, stale-data detection, a socket-conflict diagnostic, configurable interfaces/ports, and a connection test. Keep an honest status display when the game is not sending telemetry.

P2 Informative: lap/segment result, fuel check, personal best, useful stint trend, or connection restoration.

P3 Coaching: optional technique feedback, encouragement, and low-urgency observations.

Provide a reproducible short smoke test and a configurable multi-hour endurance/soak command. Run the tests available in the current environment. Clearly distinguish tests actually run from commands provided for Orange Pi/PS5 validation. An x86 run, ARM emulation, or synthetic demo is not proof of real Orange Pi audio or live GT7 compatibility.

backend/app/{telemetry,sessions,analytics,engineer,voice,storage,api,config,diagnostics}

Deliver backend and frontend source, locked dependency manifests, example configuration, database migrations, model setup, native installer, launch scripts, optional service files, a working demo/replay source, tests, and screenshots of the implemented UI when browser tooling is available.

Documentation must include README.md, INSTALL_ORANGE_PI.md, PROTOCOL.md, DATA_FIELDS.md, ARCHITECTURE.md, ALERT_RULES.md, VOICE_COMMANDS.md, PERFORMANCE.md, TROUBLESHOOTING.md, THIRD_PARTY_NOTICES.md, and IMPLEMENTATION_STATUS.md. Explain setup for a beginner: networking, PS5 address, UDP versus web ports, headset/microphone routing, model installation, starting a race, viewing the live page, retrieving a report, and diagnosing common failures.

Implement in working vertical slices:

2. Full-rate recording and a usable live dashboard.
3. Offline microphone commands, TTS, and priority/throttling scheduler.

This ordering is not permission to deliver only slice one. Build the core end-to-end experience before expanding optional features. Feature breadth must not become nonfunctional placeholder buttons.

When finished, summarize files changed, exact install/run/test commands, actual test results, measured performance if available, supported data capabilities, and any remaining hardware-only verification or incomplete features. Never claim a feature is implemented just because a stub, card, or TODO exists.
